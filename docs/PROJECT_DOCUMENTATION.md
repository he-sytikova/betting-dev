## 1. Краткое описание

Betting Dev — статическое веб-приложение на HTML, CSS и JavaScript, публикуемое через GitHub Pages. Оно предназначено для независимых экспериментов с футбольными рынками, проверки доступности исходных прогнозов, построения агрегированных вероятностей и последующего развития внутренних моделей.

Текущая активная логика основных рынков — **API-консенсус**, то есть агрегирование уже рассчитанных вероятностей, поступающих от внешних источников. Это не обученная на исторических результатах модель и не независимая оценка вероятностей с нуля.

Для рынков угловых и жёлтых карточек с 2 ноября 2026 г. действует также **экспериментальная внутренняя модель** (Poisson-регрессия по историческим данным football-data.co.uk), отображаемая на `model-v1.html` отдельным блоком и честно помеченная как исследовательская оценка.

Основные принципы проекта:

1. Dev-разработка изолирована от production.
2. CSV-файлы не коммитятся в репозиторий; обучение допускается только через задокументированный пайплайн с проверенными правами на источник.
3. Запрещённый для проекта источник Api-Football не используется.
4. Неизвестные или отсутствующие вероятности не генерируются искусственно.
5. Рынки с недостаточным покрытием не выдаются за готовую модель.
6. Результаты API-источников агрегируются только при совпадении матча и соответствующего рынка/линии.
7. Красные карточки и точный счёт исключены из прогнозного интерфейса.
8. Форы могут оставаться частью внутренних расчётов в других экспериментальных компонентах, но в текущих активных таблицах не показываются.
9. Угловые и жёлтые карточки вынесены на отдельную страницу.
10. Любое использование данных для обучения должно соответствовать отдельной проверке прав и условий источника.

## 4. Источники данных и поток обновления

### 4.1. Текущий входной набор

Основной вход для интерфейса — корневой файл `data.json`. Он содержит массив `predictions` с прогнозными записями и метаданными снимка, например датой и временем генерации.

В актуальном процессе dev не обращается напрямую к API каждого поставщика. Workflow получает опубликованный JSON-снимок из production:

`https://raw.githubusercontent.com/he-sytikova/betting/main/data.json`

Это важное архитектурное ограничение: dev отображает и анализирует доступные в этом снимке записи. Состав данных и покрытие рынков зависят от production-снимка и его источников.

### 4.2. Известные идентификаторы источников

В данных и истории интеграций встречаются:

- **BSD** — источник прогнозов/матчевых данных Bzzoiro.
- **SStats** — источник прогнозов/матчевых данных SStats.
- **Euro365** — источник прогнозов/матчевых данных Euro365.
- **FB_DATA** — Football-data.org. Это отдельный поставщик, не football-data.co.uk.
- **FOOTBALL_DATA_CO_UK** — football-data.co.uk, исторические поматчевые данные (результаты, угловые, карточки, судьи). Используется только обучающим пайплайном внутренней модели (раздел 7.5) по отдельному решению владельца с ограничениями (раздел 9).

Исторически в production использовались переменные доступа BSD_TOKEN, SSTATS_TOKEN и FD_DATA_TOKEN; Euro365 имел отдельные учётные данные. Dev не должен копировать секреты или токены в репозиторий. Секреты, если они понадобятся для отдельной интеграции, должны храниться в GitHub Actions Secrets и использоваться только в соответствующем workflow.

**Api-Football исключён из проекта.** Не добавлять его обратно в код, workflows, источники или fallback-логику.

### 4.3. Обновление расписания

Файл `.github/workflows/refresh-dev-fixtures.yml`:

- запускается по расписанию каждые два часа (cron `17 */2 * * *`);
- также поддерживает ручной запуск;
- скачивает production `data.json`;
- проверяет наличие `date`, массива `predictions` и хотя бы одной будущей записи;
- отказывается заменять dev-снимок, если будущих событий нет;
- запускает архиватор завершённых матчей;
- сохраняет обновлённые данные в dev-репозитории коммитом от GitHub Actions.

В workflow включены повторные попытки загрузки. Конкурирующие запуски объединены через concurrency-группу, чтобы два refresh-процесса не перезаписывали друг друга одновременно.

### 4.4. Часовой пояс

В текущем интерфейсном модуле время матча форматируется с часовым поясом `Europe/Moscow` и подписью «Время МСК». При изменении этого поведения необходимо синхронно обновить подпись, форматирование и документацию. Исходное время матча при этом должно оставаться машинно-разбираемым значением, а не локализованной строкой.

## 5. Алгоритм API-консенсуса

Основная реализация находится в `api-consensus.js`.

### 5.1. Нормализация названий команд

Функция `norm()`:

- приводит строку к нижнему регистру;
- нормализует Unicode и удаляет диакритические знаки;
- заменяет амперсанд на слово `and`;
- удаляет распространённые клубные приставки/суффиксы: FC, AFC, CF, SC, SV, FK, SK, Club, The;
- заменяет прочую пунктуацию пробелами;
- схлопывает повторные пробелы.

Нормализация помогает сопоставлять варианты написания названий, но сама по себе не является полноценным алгоритмом идентификации команд.

### 5.2. Сопоставление матчей

В текущей версии матчи группируются по точному ключу:

`время матча | нормализованная домашняя команда | нормализованная гостевая команда`

Условия:

- время должно успешно разбираться через `Date.parse`;
- матч должен быть будущим на момент расчёта;
- обе команды должны иметь непустые нормализованные названия;
- порядок «хозяева — гости» сохраняется.

**Важно:** время сравнивается точно, без допуска в несколько минут. Если два источника передали один матч с разными kickoff timestamp, текущий алгоритм может не объединить их. Это осознанно более безопасное поведение, чем ошибочное объединение похожих матчей. Будущее улучшение сопоставления должно включать проверку уникальности кандидата и защиту от неоднозначных матчей; нельзя безусловно склеивать события только по названиям команд.

### 5.3. Разбор и нормализация 1X2

Парсер `parse1x2()` принимает строку, содержащую ровно три распознаваемых значения:

- П1;
- X;
- П2.

Каждое значение должно быть числом от 0 до 100 процентов. Сумма исходных вероятностей должна находиться в диапазоне 85–115%. После этого значения нормализуются делением на их сумму, чтобы итоговая тройка давала 100%.

Если один из исходов отсутствует, строка не распознаётся. Если сумма слишком далека от 100%, запись отклоняется. Парсер не пытается угадывать отсутствующие значения.

### 5.4. Усреднение 1X2

Для каждого сгруппированного матча собираются распознанные тройки 1X2. Для каждой позиции рассчитывается простое арифметическое среднее нормализованных вероятностей:

[
P_{consensus}(H)=\frac{1}{N}\sum_{i=1}^{N}P_i(H)
]

Аналогично для ничьей и победы гостей.

Это **простое среднее прогнозов**, а не взвешенная модель. Источники не получают веса за историческую точность, объём данных или калибровку. До появления надёжной оценки качества нельзя называть такой консенсус оптимальным или статистически откалиброванным.

### 5.5. Производные рынки

Из усреднённой тройки 1X2 рассчитываются:

- 1X = П1 + X;
- X2 = X + П2;
- 12 = П1 + П2;
- DNB П1 = П1 / (П1 + П2);
- DNB П2 = П2 / (П1 + П2).

DNB нормируется на исходы без ничьей. Если исходная тройка отсутствует, производные вероятности не выводятся.

### 5.6. Тоталы голов

Тоталы разбираются из полей `totalGoals` и `underGoals`. Поддерживается формат вида `ТБ 2.5: 71.6%` и `ТМ 2.5: 28.4%`.

Агрегирование выполняется только для совпадающих ключей направления и линии. Например, ТБ 2.5 не смешивается с ТМ 2.5, ТБ 1.5 или ТБ 3.5.

Для каждой линии рассчитывается простое среднее только по записям, которые действительно содержат это значение. Отсутствие линии у поставщика не означает 0%.

### 5.7. Угловые

Текущий парсер угловых извлекает линии и проценты из поля `corners`. В интерфейсе значение помечается как «ТБ угл.» и показывается только при наличии распознанной вероятности.

На момент документирования покрытие угловых ограничено BSD. Поэтому эти значения являются прогнозом одного источника, а не межисточниковым консенсусом. Это различие должно оставаться явно обозначенным в UI.

На странице `model-v1.html` внешние данные больше не выводятся: страница показывает только экспериментальную внутреннюю модель угловых (раздел 7.5).

### 5.8. Жёлтые карточки

В текущем входном снимке отсутствуют распознаваемые вероятности жёлтых карточек от внешних источников. Поэтому API-таблица их не рассчитывает и не подставляет.

С 2 ноября 2026 г. вероятности ЖК выводит экспериментальная внутренняя модель (раздел 7.5) — отдельным блоком и только для матчей, найденных в обучающих данных. Наличие ключа `yellowCards` в архивной схеме по-прежнему не означает, что источник передаёт значения.

### 5.9. Отображение вероятностей

Функция `stackedCell()` выводит каждый исход отдельной строкой внутри ячейки таблицы. В частности:

- П1, X и П2 не склеиваются в одну строку;
- 1X, X2, 12 и DNB показываются раздельно;
- каждая линия тотала выводится отдельно;
- каждая линия угловых выводится отдельно.

Индивидуальная вероятность выше 65% подсвечивается. Подсветка относится к конкретной строке/значению, а не ко всей строке матча. Порог 65% — визуальный ориентир интерфейса, а не доказательство value, точности или прибыльности ставки.

### 5.10. Источники и счётчик

В таблице выводится список уникальных имён источников. Поле `sourceCount` в текущей реализации считает число исходных записей в группе, а не число уникальных поставщиков. При интерпретации покрытия ориентироваться на список `sourceNames`, а не трактовать число записей как число независимых источников.

Количество будущих матчей зависит от времени запуска и фильтрации уже начавшихся событий. Не следует переносить старые количественные значения на новый снимок без повторного подсчёта.

## 7. Внутренние модели и старые CSV-артефакты

### 7.1. Почему прежние модели отключены

Ранее в проекте существовали обученные компоненты:

- `goals-model.js`;
- `model-v1.js`.

Их артефакты были связаны с историческим CSV-датасетом. Эти обученные артефакты нельзя считать действующими, корректными или разрешёнными для использования.

Загрузчики старых моделей оставлены отключёнными с пояснением, что прежние CSV-обученные версии приостановлены. Не включать их обратно и не ссылаться на их прежние метрики как на действующие результаты. Это относится и к `data/goals_markets_models.json`: цели-рынки внутренней моделью сейчас не обслуживаются.

### 7.2. Удаление CSV

В dev-репозитории запрещено коммитить CSV-файлы. В истории Git могут оставаться старые коммиты, в которых такие файлы существовали; это не означает, что они используются текущей веткой или активными workflows.

Проверочный workflow дополнительно проверяет отсутствие файлов с расширением `.csv` в рабочем дереве. Обучающий пайплайн внутренней модели (раздел 7.5) скачивает исходные CSV только в runner GitHub Actions и коммитит исключительно производные JSON-артефакты.

### 7.3. Приостановленные исторические workflows

Следующие процессы были переведены в ручной/приостановленный режим и не должны запускаться как автоматический pipeline:

- `download-historical-csvs.yml`;
- `build-historical-dataset.yml`;
- `track-internal-predictions.yml`.

Не восстанавливать автоматические скачивания CSV и обучение через эти старые workflows. Актуальный разрешённый путь переобучения — отдельный workflow `retrain-corners-cards.yml` (раздел 10.4).

### 7.4. Что считается внутренней моделью

API-консенсус не является внутренней моделью. Чтобы считать новый компонент собственной моделью, он должен иметь воспроизводимую процедуру расчёта/обучения, документированный источник данных, допустимое происхождение данных, тесты, отчёт оценки на отложенной выборке и мониторинг качества после запуска.

### 7.5. Внутренняя модель угловых и жёлтых карточек (с 2 ноября 2026 г.)

**Назначение.** Экспериментальная собственная оценка тоталов угловых и жёлтых карточек для предстоящих матчей из `data.json`. Является единственным содержимым страницы `model-v1.html` и не смешивается с API-данными источников.

**Данные.** Поматчевая история football-data.co.uk (`mmz4281/{сезон}/{лига}.csv`), сезоны 2000/01–2025/26+, лиги E0, E1, E2, E3, SC0, D1, I1, SP1, F1 (N1 исключена из-за низкого покрытия целевых полей). Используются колонки результатов, угловых (HC/AC), жёлтых карточек (HY/AY), фолов, ударов и судей. Права на источник — отдельное решение владельца от 2 ноября 2026 г., зафиксировано в `data/source_eligibility.json` вместе с ограничениями (лёгкое скачивание не чаще раза в неделю, сырые CSV не публикуются).

**Пайплайн (воспроизводимый).**

1. `scripts/models/download-football-data-csvs.py` — лёгкое скачивание сезонных CSV в `data/raw/football-data/` (только в runner, не коммитится).
2. `scripts/models/build-historical-dataset.py` — сборка `data/corners_cards_training.csv` с leakage-safe признаками: скользящие средние команды за 5/10 матчей (угловые «заработал/отдал», карточки, голы, фолы, удары), лиговые средние и статистика судьи строго по прошлым матчам.
3. `scripts/models/train-corners-cards.py` — обучение Poisson-регрессии (scikit-learn `PoissonRegressor`) с хронологическим разбиением train/validation/test, подбором регуляризации и абляцией судейских признаков только на validation; сравнение с baseline «скользящее среднее лиги» и NB2. Отчёт: `data/corners_cards_model_validation.json`.
4. `scripts/models/export-corners-cards-runtime.py` — переобучение на полной истории и экспорт `data/corners_cards_models.json` (schemaVersion 2): коэффициенты, скейлеры, медианы имputации, свежие скользящие признаки команд, лиговые средние, алиасы лиг.

**Качество на отложенной выборке (тест с 2024-07-01, ~8,2 тыс. матчей).** Poisson-регрессия незначительно, но устойчиво лучше лигового baseline по Poisson-девиансе: угловые 1.184 против 1.194, ЖК 1.132 против 1.152; по ЖК также лучше MAE (1.585 против 1.603). Это умеренный уровень точности: модель является исследовательским baseline, а не доказанным преимуществом.

**Инференс в браузере (`internal-model.js`).** Для каждого будущего матча из `data.json` модуль: нормализует название лиги и команд; сопоставляет их с обучающими данными через `leagueAliases`, точное совпадение, кураторский словарь алиасов (`TEAM_ALIASES`) и однозначный substring-fallback внутри лиги; при неоднозначности или отсутствии команды прогноз не выводится. Далее линейный предиктор с теми же скейлерами/медианами даёт λ, и по распределению Пуассона считаются вероятности ТБ для линий 7.5–12.5 (угловые) и 1.5–6.5 (ЖК). Судья на матч заранее неизвестен — судейские признаки импутируются медианами обучения. Минимальная история команды — 5 матчей (`runtimePolicy.minimumTeamMatches`).

**Ограничения.** Поддерживаются только перечисленные лиги; матчи остальных лиг строки не получают. Алиас `primera division` → SP1 добавлен под нейминг FB_DATA и защищён проверкой команд внутри лиги; при появлении коллизий его нужно пересмотреть. Распределение Пуассона занижает дисперсию для части линий (см. `data/corners_cards_distribution_v1.json`); NB2 в рантайме пока не развёрнут.

## 8. Архив результатов без CSV

Скрипт `scripts/models/archive-provider-results.mjs` сохраняет завершённые результаты в JSONL:

- вход: корневой `data.json`;
- каталог: `data/results-ledger/`;
- файл: `YYYY-MM-DD.jsonl`;
- одна запись — одна строка JSON.

### 8.1. Что попадает в архив

Скрипт проверяет поле `actualResult`. Оно должно содержать маркер завершения (например, FT/ФТ/FINISHED) и счёт. Из него извлекаются:

- голы хозяев;
- голы гостей;
- сумма голов;
- фактический исход П1/X/П2;
- угловые, если они присутствуют в распознаваемом формате.

Также сохраняются идентификатор события, источник, команды, лига, время матча, прогнозные поля и исходная строка результата.

### 8.2. Дедупликация

Ключ дедупликации — сочетание `source` и `eventId` в рамках дневного файла. Повторная обработка одного и того же события не должна добавлять вторую запись в этот файл.

### 8.3. Ограничения архива

- Текущий парсер не извлекает фактическое число жёлтых карточек.
- Архивирование зависит от того, передаёт ли входной снимок завершённый результат в поддерживаемом формате.
- Если в снимке нет подходящих завершённых матчей, файл может не появиться или остаться пустым.
- JSONL-архив результатов не является автоматически разрешённым датасетом для обучения: перед использованием нужно проверить права источника и происхождение каждой записи.
- Архивирование прогнозных полей не означает разрешение на их бессрочное хранение, перераспределение или обучение.

## 9. Политика прав на данные

Файл `data/source_eligibility.json` — реестр проверки источников и их допустимого назначения. Перед любым новым сбором, архивированием, построением датасета или обучением необходимо сверяться с ним и с актуальными условиями поставщика.

Текущие статусы в реестре:

| Источник | Статус обучения | Практическое правило |
|---|---|---|
| BSD | `conditional_review` | Есть положения о хранении/исследованиях/ML, но остаются вопросы upstream-прав; требуется проверка |
| SStats | `terms_not_found` | Не обучать до получения явного разрешения |
| Euro365 | `not_explicitly_granted` | Не обучать без письменного разрешения на хранение и ML |
| FB_DATA (football-data.org) | `not_explicitly_granted` | Не обучать без уточнения прав на историю и ML |
| FOOTBALL_DATA_CO_UK | `permitted_by_owner_decision_with_restrictions` | Только пайплайн угловых/ЖК; лёгкое скачивание ≤1 раза в неделю; CSV не коммитить; пересмотр при возражениях поставщика |
| OPEN_MATCHDAY | `not_explicitly_granted` | Только кандидат после проверки происхождения каждой записи и upstream-прав |
| THESTATSAPI | `not_explicitly_granted` | Не подключать к обучению без письменного разрешения на backfill, хранение и ML |

Особенно важно не смешивать:

- `FB_DATA` = football-data.org;
- `FOOTBALL_DATA_CO_UK` = football-data.co.uk.

Это разные источники с разными условиями.

**Фиксация решения по FOOTBALL_DATA_CO_UK (2 ноября 2026 г.).** Fair Data Usage Policy поставщика предназначает бесплатные файлы частным лицам для личных/академических целей при ручном или лёгком скачивании (не чаще двух раз в неделю) и не разрешает тяжёлые автоматические выгрузки и коммерческие обучающие продукты. Владелец репозитория явно разрешил использование источника для исследовательского пайплайна угловых/ЖК в рамках персонального проекта, приняв ответственность за эту трактовку. Принятые меры: скачивание раз в неделю с паузами и описательным User-Agent; сырые CSV никогда не коммитятся (CI падает при появлении `.csv`); публикуются только производные коэффициенты и агрегированная статистика. При возражении поставщика или выходе проекта за рамки личного исследования решение пересматривается, пайплайн останавливается.

### 9.1. Обязательная процедура для нового источника

Перед использованием источника для обучения или длительного хранения:

1. Зафиксировать точное юридическое лицо поставщика и URL актуальных условий.
2. Проверить разрешение на получение исторических данных и частоту запросов.
3. Проверить право на долгосрочное хранение и создание собственной базы.
4. Проверить прямое разрешение на model training, machine learning, backtesting и evaluation.
5. Проверить права на derived outputs и их публичное отображение.
6. Проверить upstream-поставщиков и ограничения на данные третьих лиц.
7. Уточнить, что происходит с данными и производными результатами после отмены подписки.
8. Обновить `data/source_eligibility.json` с датой и обоснованием.
9. Только после этого добавлять источник в обучающий workflow.

Успешная техническая загрузка данных не означает, что их юридически разрешено использовать для обучения.

## 15. Известные ограничения и технический долг

### 15.1. Точное время в ключе матча

Текущее сопоставление требует одинакового timestamp. Это может снижать количество объединённых источников. Следующий разумный шаг — отдельный модуль сопоставления с допуском по времени, нормализацией названий и строгой проверкой однозначности. Ошибочное объединение двух разных матчей хуже, чем отсутствие консенсуса.

### 15.2. Простое среднее без оценки надёжности

Сейчас источники имеют одинаковый вес. Нет проверенной калибровки и оценки Brier score/log loss по каждому источнику на достаточно большой и независимой выборке. Нельзя назначать веса источникам на основании впечатления или малого количества матчей.

### 15.3. Ограниченное покрытие внутренней модели

Внутренняя модель угловых/ЖК обслуживает только девять европейских лиг из обучающих данных. Матчи остальных лиг (Португалия, Бразилия, Америка и др.) прогноза не получают — это осознанное ограничение, а не ошибка отображения. Сопоставление команд зависит от кураторского словаря алиасов; новые команды и переименования требуют пополнения `TEAM_ALIASES`. Сравнение внутренней модели с прогнозами BSD на общих матчах ещё не автоматизировано — это следующий шаг оценки качества.

### 15.4. Архив результатов пока ограничен

Архиватор сохраняет только распознаваемые завершённые результаты и не извлекает фактические жёлтые карточки. Нужны контроль полноты, аудит ошибок парсинга, сопоставление прогнозов с фактическими событиями и подтверждение прав на использование данных.

### 15.5. Снимок зависит от production

Dev получает текущий `data.json` из production. Изменения формата production-файла могут повлиять на dev. Желательно добавить версионирование схемы и проверку обязательных полей при каждом обновлении.

### 15.6. Отсутствует полноценный backtesting

Наличие архивных результатов, API-консенсуса и валидационного отчёта внутренней модели ещё не означает, что система прошла backtesting в продовых условиях. Для этого необходимы сохранённые прогнозы, корректные фактические результаты, временное разделение выборок, проверка калибровки и анализ по лигам/рынкам/источникам. Валидация внутренней модели выполнена на хронологически отложенной выборке, но это исследовательская оценка, а не ROI-тест.

## 16. Рекомендуемый дальнейший план

Порядок работ, который минимизирует риск ложных выводов:

### Этап A — качество сопоставления событий
- Добавить диагностический отчёт по непарным и объединённым событиям.
- Реализовать безопасное сопоставление при небольшом расхождении времени только для уникальной пары команд.
- Отдельно тестировать одинаковые команды в разных турнирах/датах и неоднозначные пары.
- Не объединять события при конфликте домашней/гостевой стороны.

### Этап B — диагностика консенсуса
- Показывать число уникальных источников для каждого матча и рынка.
- Разделять «одноисточниковый прогноз» и «консенсус».
- Показывать диапазон расхождения источников, медиану и среднее, не подменяя ими друг друга.
- Маркировать подозрительные/неполные тройки вероятностей.
- Не скрывать низкое покрытие за общим количеством записей.

### Этап C — сбор результатов и оценка качества
- Расширить разбор фактических результатов и проверять его на реальных форматах.
- Добавить журнал ошибок и отчёт по полноте архива.
- Сопоставлять сохранённый прогноз с итогом матча без утечки будущей информации.
- Считать Brier score, log loss, calibration/reliability bins и метрики по рынкам.
- Публиковать объём выборки рядом с каждой метрикой.
- Сохранять ежедневные прогнозы внутренней модели угловых/ЖК и оценивать их на фактических данных football-data.co.uk по мере публикации результатов.
- До проверки прав не использовать ограниченные данные для обучения.

### Этап D — внутренние модели
- ✅ Угловые и ЖК: первая воспроизводимая версия запущена (раздел 7.5), хронологическая валидация и отчёт приложены.
- Следующие шаги: NB2/калибровка по линиям на живых данных, сравнение с BSD на общих матчах, расширение лиг при достаточном покрытии.
- Исходы 1X2: отдельная модель на разрешённых данных (openfootball, ClubElo, international_results) — кандидат на следующую итерацию; сравнивать с простым baseline и API-консенсусом.
- Вводить модель в интерфейс только после воспроизводимой оценки и достаточного покрытия.

### Этап E — надёжность эксплуатации
- Версионировать схему `data.json`.
- Добавить мониторинг устаревшего снимка и ошибок загрузки.
- Проверять, что Pages опубликован после успешной валидации.
- Сохранять краткий changelog и дату последнего успешного расчёта.

## 17. Термины

- **API-консенсус** — простое агрегирование прогнозных вероятностей нескольких API-источников.
- **Источник** — поставщик исходных данных или прогнозов, например BSD.
- **Исходная запись** — одна строка прогноза в `data.json`.
- **Уникальный источник** — distinct provider name после группировки матча.
- **Линия** — порог тотала, например 2.5 гола или 9.5 угловых.
- **Двойной шанс** — объединение двух исходов 1X2.
- **DNB** — ставка без учёта ничьей; вероятность нормируется на две неничейные стороны.
- **JSONL** — текстовый файл, где каждая строка является самостоятельным JSON-объектом.
- **Backtesting** — ретроспективная оценка прогнозов на фактических результатах.
- **Калибровка** — соответствие прогнозируемых вероятностей фактической частоте наступления событий.
- **Внутренняя модель** — воспроизводимый обученный компонент с документированным источником, тестами и отчётом оценки (сейчас: Poisson-регрессия угловых и ЖК).
- **Production** — основное приложение; **dev** — отдельная экспериментальная среда.

## 18. Ключевые правила, которые нельзя нарушать

1. Не вносить изменения в production без отдельного разрешения.
2. Не коммитить CSV в репозиторий; не включать старые отключённые модели (`goals-model.js`, `model-v1.js`, goals-артефакты).
3. Не подключать Api-Football.
4. Не выдумывать вероятности отсутствующих рынков.
5. Не выдавать один источник за консенсус.
6. Жёлтые карточки показывать только через проверенную внутреннюю модель или реальные входные вероятности.
7. Не возвращать красные карточки и точный счёт в прогнозный интерфейс.
8. Не показывать форы в активных таблицах без отдельного решения.
9. Не использовать данные для обучения вне зафиксированных в `data/source_eligibility.json` решений; изменение прав — только с датой и обоснованием.
10. Не называть API-консенсус внутренней обученной моделью.
11. Не считать визуальную подсветку вероятности выше 65% рекомендацией к ставке.
12. При каждом изменении расчёта добавлять тесты и проверять опубликованный результат.
13. Внутреннюю модель показывать только отдельным помеченным блоком и только для матчей, сопоставленных с обучающими данными.
