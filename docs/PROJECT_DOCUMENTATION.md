## 1. Краткое описание

Betting Dev — статическое веб-приложение на HTML, CSS и JavaScript, публикуемое через GitHub Pages. Оно предназначено для независимых экспериментов с футбольными рынками, проверки доступности исходных прогнозов, построения агрегированных вероятностей и последующего развития внутренних моделей.

Текущая активная логика основных рынков — **API-консенсус**, то есть агрегирование уже рассчитанных вероятностей, поступающих от внешних источников. Это не обученная на исторических результатах модель и не независимая оценка вероятностей с нуля.

Для рынков угловых и жёлтых карточек с 2 ноября 2026 г. действует также **экспериментальная внутренняя модель** (Poisson-регрессия по историческим данным football-data.co.uk), отображаемая на `model-v1.html` отдельным блоком и честно помеченная как исследовательская оценка. Аналогичная внутренняя модель исходов (П1/Х/П2, двойные шансы) и тоталов голов (общий и индивидуальные) действует на странице `goals-model.html`. Внутренняя модель тоталов фолов, ударов и ударов в створ действует на странице `stats-model.html`.

Основные принципы проекта:

1. Dev-разработка изолирована от production.
2. CSV-файлы не коммитятся в репозиторий; обучение допускается только через задокументированный пайплайн с проверенными правами на источник.
3. Запрещённый для проекта источник Api-Football не используется.
4. Неизвестные или отсутствующие вероятности не генерируются искусственно.
5. Рынки с недостаточным покрытием не выдаются за готовую модель.
6. Результаты API-источников агрегируются только при совпадении матча и соответствующего рынка/линии.
7. Красные карточки и точный счёт исключены из прогнозного интерфейса.
8. Форы могут оставаться частью внутренних расчётов в других экспериментальных компонентах, но в текущих активных таблицах не показываются.
9. Угловые и жёлтые карточки вынесены на отдельную страницу.
10. Любое использование данных для обучения должно соответствовать отдельной проверке прав и условий источника.

## 4. Источники данных и поток обновления

### 4.1. Текущий входной набор

Основной вход для интерфейса — корневой файл `data.json`. Он содержит массив `predictions` с прогнозными записями и метаданными снимка, например датой и временем генерации.

В актуальном процессе dev не обращается напрямую к API каждого поставщика. Workflow получает опубликованный JSON-снимок из production:

`https://raw.githubusercontent.com/he-sytikova/betting/main/data.json`

Это важное архитектурное ограничение: dev отображает и анализирует доступные в этом снимке записи. Состав данных и покрытие рынков зависят от production-снимка и его источников.

### 4.2. Известные идентификаторы источников

В данных и истории интеграций встречаются:

- **BSD** — источник прогнозов/матчевых данных Bzzoiro.
- **SStats** — источник прогнозов/матчевых данных SStats.
- **Euro365** — источник прогнозов/матчевых данных Euro365.
- **FB_DATA** — Football-data.org. Это отдельный поставщик, не football-data.co.uk.
- **FOOTBALL_DATA_CO_UK** — football-data.co.uk, исторические поматчевые данные (результаты, угловые, карточки, судьи). Используется только обучающим пайплайном внутренней модели (раздел 7.5) по отдельному решению владельца с ограничениями (раздел 9).

Исторически в production использовались переменные доступа BSD_TOKEN, SSTATS_TOKEN и FD_DATA_TOKEN; Euro365 имел отдельные учётные данные. Dev не должен копировать секреты или токены в репозиторий. Секреты, если они понадобятся для отдельной интеграции, должны храниться в GitHub Actions Secrets и использоваться только в соответствующем workflow.

**Api-Football исключён из проекта.** Не добавлять его обратно в код, workflows, источники или fallback-логику.

### 4.3. Обновление расписания

Файл `.github/workflows/refresh-dev-fixtures.yml`:

- запускается по расписанию каждые два часа (cron `17 */2 * * *`);
- также поддерживает ручной запуск;
- скачивает production `data.json`;
- проверяет наличие `date`, массива `predictions` и хотя бы одной будущей записи;
- отказывается заменять dev-снимок, если будущих событий нет;
- запускает архиватор завершённых матчей;
- сохраняет обновлённые данные в dev-репозитории коммитом от GitHub Actions.

В workflow включены повторные попытки загрузки. Конкурирующие запуски объединены через concurrency-группу, чтобы два refresh-процесса не перезаписывали друг друга одновременно.

### 4.4. Часовой пояс

В текущем интерфейсном модуле время матча форматируется с часовым поясом `Europe/Moscow` и подписью «Время МСК». При изменении этого поведения необходимо синхронно обновить подпись, форматирование и документацию. Исходное время матча при этом должно оставаться машинно-разбираемым значением, а не локализованной строкой.

## 5. Алгоритм API-консенсуса

Основная реализация находится в `api-consensus.js`.

### 5.1. Нормализация названий команд

Функция `norm()`:

- приводит строку к нижнему регистру;
- нормализует Unicode и удаляет диакритические знаки;
- заменяет амперсанд на слово `and`;
- удаляет распространённые клубные приставки/суффиксы: FC, AFC, CF, SC, SV, FK, SK, Club, The;
- заменяет прочую пунктуацию пробелами;
- схлопывает повторные пробелы.

Нормализация помогает сопоставлять варианты написания названий, но сама по себе не является полноценным алгоритмом идентификации команд.

### 5.2. Сопоставление матчей

В текущей версии матчи группируются по точному ключу:

`время матча | нормализованная домашняя команда | нормализованная гостевая команда`

Условия:

- время должно успешно разбираться через `Date.parse`;
- матч должен быть будущим на момент расчёта;
- обе команды должны иметь непустые нормализованные названия;
- порядок «хозяева — гости» сохраняется.

**Важно:** время сравнивается точно, без допуска в несколько минут. Если два источника передали один матч с разными kickoff timestamp, текущий алгоритм может не объединить их. Это осознанно более безопасное поведение, чем ошибочное объединение похожих матчей. Будущее улучшение сопоставления должно включать проверку уникальности кандидата и защиту от неоднозначных матчей; нельзя безусловно склеивать события только по названиям команд.

### 5.3. Разбор и нормализация 1X2

Парсер `parse1x2()` принимает строку, содержащую ровно три распознаваемых значения:

- П1;
- X;
- П2.

Каждое значение должно быть числом от 0 до 100 процентов. Сумма исходных вероятностей должна находиться в диапазоне 85–115%. После этого значения нормализуются делением на их сумму, чтобы итоговая тройка давала 100%.

Если один из исходов отсутствует, строка не распознаётся. Если сумма слишком далека от 100%, запись отклоняется. Парсер не пытается угадывать отсутствующие значения.

### 5.4. Усреднение 1X2

Для каждого сгруппированного матча собираются распознанные тройки 1X2. Для каждой позиции рассчитывается простое арифметическое среднее нормализованных вероятностей:

[
P_{consensus}(H)=\frac{1}{N}\sum_{i=1}^{N}P_i(H)
]

Аналогично для ничьей и победы гостей.

Это **простое среднее прогнозов**, а не взвешенная модель. Источники не получают веса за историческую точность, объём данных или калибровку. До появления надёжной оценки качества нельзя называть такой консенсус оптимальным или статистически откалиброванным.

### 5.5. Производные рынки

Из усреднённой тройки 1X2 рассчитываются:

- 1X = П1 + X;
- X2 = X + П2;
- 12 = П1 + П2;
- DNB П1 = П1 / (П1 + П2);
- DNB П2 = П2 / (П1 + П2).

DNB нормируется на исходы без ничьей. Если исходная тройка отсутствует, производные вероятности не выводятся.

### 5.6. Тоталы голов

Тоталы разбираются из полей `totalGoals` и `underGoals`. Поддерживается формат вида `ТБ 2.5: 71.6%` и `ТМ 2.5: 28.4%`.

Агрегирование выполняется только для совпадающих ключей направления и линии. Например, ТБ 2.5 не смешивается с ТМ 2.5, ТБ 1.5 или ТБ 3.5.

Для каждой линии рассчитывается простое среднее только по записям, которые действительно содержат это значение. Отсутствие линии у поставщика не означает 0%.

### 5.7. Угловые

Текущий парсер угловых извлекает линии и проценты из поля `corners`. В интерфейсе значение помечается как «ТБ угл.» и показывается только при наличии распознанной вероятности.

На момент документирования покрытие угловых ограничено BSD. Поэтому эти значения являются прогнозом одного источника, а не межисточниковым консенсусом. Это различие должно оставаться явно обозначенным в UI.

На странице `model-v1.html` внешние данные больше не выводятся: страница показывает только экспериментальную внутреннюю модель угловых (раздел 7.5).

### 5.8. Жёлтые карточки

В текущем входном снимке отсутствуют распознаваемые вероятности жёлтых карточек от внешних источников. Поэтому API-таблица их не рассчитывает и не подставляет.

С 2 ноября 2026 г. вероятности ЖК выводит экспериментальная внутренняя модель (раздел 7.5) — отдельным блоком и только для матчей, найденных в обучающих данных. Наличие ключа `yellowCards` в архивной схеме по-прежнему не означает, что источник передаёт значения.

### 5.9. Отображение вероятностей

Функция `stackedCell()` выводит каждый исход отдельной строкой внутри ячейки таблицы. В частности:

- П1, X и П2 не склеиваются в одну строку;
- 1X, X2, 12 и DNB показываются раздельно;
- каждая линия тотала выводится отдельно;
- каждая линия угловых выводится отдельно.

Индивидуальная вероятность выше 65% подсвечивается. Подсветка относится к конкретной строке/значению, а не ко всей строке матча. Порог 65% — визуальный ориентир интерфейса, а не доказательство value, точности или прибыльности ставки.

### 5.10. Источники и счётчик

В таблице выводится список уникальных имён источников. Поле `sourceCount` в текущей реализации считает число исходных записей в группе, а не число уникальных поставщиков. При интерпретации покрытия ориентироваться на список `sourceNames`, а не трактовать число записей как число независимых источников.

## 7. Внутренние модели и старые CSV-артефакты

### 7.1. Почему прежние модели отключены

Ранее в проекте существовали обученные компоненты:

- `goals-model.js`;
- `model-v1.js`.

Их артефакты были связаны с историческим CSV-датасетом. Эти обученные артефакты нельзя считать действующими, корректными или разрешёнными для использования.

Загрузчики старых моделей оставлены отключёнными с пояснением, что прежние CSV-обученные версии приостановлены. Не включать их обратно и не ссылаться на их прежние метрики как на действующие результаты. С 2 ноября 2026 г. `data/goals_markets_models.json` заново формируется новым разрешённым пайплайном (раздел 7.6) и не имеет отношения к старому CSV-артефакту.

### 7.2. Удаление CSV

В dev-репозитории запрещено коммитить CSV-файлы. В истории Git могут оставаться старые коммиты, в которых такие файлы существовали; это не означает, что они используются текущей веткой или активными workflows.

Проверочный workflow дополнительно проверяет отсутствие файлов с расширением `.csv` в рабочем дереве. Обучающий пайплайн внутренней модели (раздел 7.5) скачивает исходные CSV только в runner GitHub Actions и коммитит исключительно производные JSON-артефакты.

### 7.3. Приостановленные исторические workflows

Следующие процессы были переведены в ручной/приостановленный режим и не должны запускаться как автоматический pipeline:

- `download-historical-csvs.yml`;
- `build-historical-dataset.yml`.

Не восстанавливать автоматические скачивания CSV и обучение через эти старые workflows. Актуальный разрешённый путь переобучения — отдельный workflow `retrain-corners-cards.yml` (раздел 10.4). Workflow `track-internal-predictions.yml` 2 ноября 2026 г. возвращён в активный режим в новой редакции (раздел 7.8): прежняя приостановка относилась к периоду до авторизации источника football-data.co.uk и более не применима.

### 7.4. Что считается внутренней моделью

API-консенсус не является внутренней моделью. Чтобы считать новый компонент собственной моделью, он должен иметь воспроизводимую процедуру расчёта/обучения, документированный источник данных, допустимое происхождение данных, тесты, отчёт оценки на отложенной выборке и мониторинг качества после запуска.

### 7.5. Внутренняя модель угловых и жёлтых карточек (с 2 ноября 2026 г.)

**Назначение.** Экспериментальная собственная оценка тоталов угловых и жёлтых карточек для предстоящих матчей из `data.json`. Является единственным содержимым страницы `model-v1.html` и не смешивается с API-данными источников.

**Данные.** Поматчевая история football-data.co.uk (`mmz4281/{сезон}/{лига}.csv`), сезоны 2000/01–2026/27, 18 лиг: E0, E1, E2, E3, SC0, SC1, D1, D2, I1, I2, SP1, SP2, F1, F2, B1, P1, T1, G1 (N1 остаётся в датасете для исследования голов/исходов, но исключена из статистических моделей из-за исторического покрытия целевых полей 34.75%). С 3 ноября 2026 г. общий датасет дополнительно включает 5 results-only лиг (RUS, BRA, USA, NOR, SWE из `/new/{код}.csv`): у них есть только результат и закрывающие коэффициенты, все флаги доступности статистики равны нулю, поэтому они обучают только модель голов (раздел 7.6) и никогда не попадают в обучение статистических моделей. С сезона 2020/21 покрытие статистических полей во всех 18 лигах ~99–100%; более ранние сезоны покрыты частично, строки без целевых полей отфильтровываются флагами доступности. Используются колонки результатов, угловых (HC/AC), жёлтых карточек (HY/AY), фолов, ударов и судей. Права на источник — отдельное решение владельца от 2 ноября 2026 г., зафиксировано в `data/source_eligibility.json` вместе с ограничениями (лёгкое скачивание не чаще раза в неделю, сырые CSV не публикуются).

**Пайплайн (воспроизводимый).**

1. `scripts/models/download-football-data-csvs.py` — лёгкое скачивание сезонных CSV в `data/raw/football-data/` (только в runner, не коммитится).
2. `scripts/models/build-historical-dataset.py` — сборка `data/corners_cards_training.csv` с leakage-safe признаками: скользящие средние команды за 5/10 матчей (угловые «заработал/отдал», карточки, голы, фолы, удары), лиговые средние и статистика судьи строго по прошлым матчам. Обработка глобально хронологическая (все лиги одним днём за раз); скользящие истории команд ключованы страновой семьёй, поэтому клуб сохраняет форму при переходе между дивизионами одной страны (вылет/выход), а лиговые средние и судейские статистики остаются по-лиговыми.
3. `scripts/models/train-corners-cards.py` — обучение Poisson-регрессии (scikit-learn `PoissonRegressor`) с хронологическим разбиением train/validation/test, подбором регуляризации и абляцией судейских признаков только на validation; сравнение с baseline «скользящее среднее лиги» и с NB2-переобучением (GLM statsmodels в том же трансформированном пространстве признаков, дисперсия из остатков обучающей части). Развёртываемое распределение выбирается по среднему logLoss линий на validation с мёртвой зоной 0.0005 в пользу Poisson. Отдельно оценивается изотоническая калибровка каждой линии: развёртывается только при честном кросс-фит выигрыше внутри validation (обучение на ранней половине, оценка на поздней) выше той же мёртвой зоны; тест используется только для отчётности. Отчёт: `data/corners_cards_model_validation.json`.
4. `scripts/models/export-corners-cards-runtime.py` — переобучение на полной истории и экспорт `data/corners_cards_models.json` (schemaVersion 2): коэффициенты (для NB2 — из GLM-переобучения), скейлеры, медианы имputации, свежие скользящие признаки команд, лиговые средние, алиасы лиг, `nbAlpha` и узлы калибраторов, если они развёрнуты.

**Качество на отложенной выборке (тест с 2024-07-01, ~14,6 тыс. матчей, 18 лиг).** Poisson-регрессия незначительно, но устойчиво лучше лигового baseline по Poisson-девиансе: угловые 1.177 против 1.190, ЖК 1.162 против 1.178. По лигам: угловые лучше baseline в 17 из 18 лиг (I1 хуже на 0.003), ЖК лучше в 12 из 18 (расхождения не хуже 0.021 при n≥424 — в пределах шума). Выбор распределения (2 ноября 2026 г.): угловые переведены на NB2 — средний logLoss линий на validation 0.61121 против 0.61220 у Poisson, на тесте 0.6114 против 0.6122 (девианса среднего сопоставима: 1.1770 и 1.1769); ЖК остаются Poisson (validation 0.50788 против 0.50815 у NB2). Изотоническая калибровка линий не развёрнута: кросс-фит выигрыш внутри validation отрицателен (−0.029 угловые, −0.0001 ЖК), то есть сырые вероятности уже откалиброваны хорошо, а изотоника подстраивается под шум. Это умеренный уровень точности: модель является исследовательским baseline, а не доказанным преимуществом.

**Инференс в браузере (`internal-model.js`).** Для каждого будущего матча из `data.json` модуль: нормализует название лиги и команд; сопоставляет их с обучающими данными через `leagueAliases`, точное совпадение, кураторский словарь алиасов (`TEAM_ALIASES`) и однозначный substring-fallback внутри лиги; при неоднозначности или отсутствии команды прогноз не выводится. Далее линейный предиктор с теми же скейлерами/медианами даёт λ, и по распределению рынка (`type` в экспорте: Poisson или NB2 с параметром `nbAlpha`) считаются вероятности ТБ для линий 7.5–12.5 (угловые) и 1.5–6.5 (ЖК); если для линии экспортирован калибратор, вероятность дополнительно пропускается через него. Судья на матч заранее неизвестен — судейские признаки импутируются медианами обучения. Минимальная история команды — 5 матчей (`runtimePolicy.minimumTeamMatches`).

**Ограничения.** Поддерживаются только перечисленные лиги; матчи остальных лиг строки не получают. Алиас `primera division` → SP1 добавлен под нейминг FB_DATA и защищён проверкой команд внутри лиги; при появлении коллизий его нужно пересмотреть. Пуассоновское занижение дисперсии частично снято переводом угловых на NB2 (с 2 ноября 2026 г.); для ЖК NB2 не дал выигрыша на validation.

### 7.6. Внутренняя модель исходов и тоталов голов (с 2 ноября 2026 г.)

**Назначение.** Экспериментальная собственная оценка исходов (П1, Х, П2), двойных шансов (1Х, 12, Х2), общего тотала голов (линии 1.5–4.5) и индивидуальных тоталов команд (линии 0.5–2.5) для предстоящих матчей из `data.json`. Является единственным содержимым страницы `goals-model.html` и не смешивается с API-данными источников.

**Данные.** Тот же поматчевый массив football-data.co.uk и тот же leakage-safe датасет `data/corners_cards_training.csv` (раздел 7.5): целевые поля голов (FTHG/FTAG), скользящие признаки голов, ударов, ударов в створ и угловых команд за 5/10 матчей, лиговые средние и преимущество домашнего поля. С 3 ноября 2026 г. добавлены рейтинговые признаки, вычисляемые сборщиком по семьям стран с обновлением строго после дня матча: Elo (старт 1500, K=20, домашнее преимущество 65 пунктов, множитель разницы голов 1 / 1.5 / 1.5+0.25·(N−2)) и экспоненциально затухающие рейтинги атаки/защиты по голам (период полураспада 75 дней, O(1)-агрегаты взвешенных сумм). С 3 ноября 2026 г. (этап 4) обучающий набор — 24 лиги: 18 лиг со статистикой + Нидерланды N1 + 5 results-only лиг из однофайловых выгрузок `/new/{код}.csv` (Россия RUS, Бразилия BRA, MLS США, Норвегия NOR, Швеция SWE). Адаптер results-only читает усечённую схему (Country/League/Season/Date/Home/Away/HG/AG/Res + закрывающие коэффициенты), сезон берётся из колонки `Season`; у таких матчей нет статистики и судьи, поэтому все флаги доступности равны нулю, статистические признаки импутируются медианами с индикаторами пропуска, а голы/Elo/затухающие рейтинги считаются полноценно. Закрывающие коэффициенты (PSCH/PSCD/PSCA, MaxC*, AvgC*) в сырых файлах сохраняются и предназначены для будущего бэктеста против рынка.

**Пайплайн (воспроизводимый).**

1. Общие шаги 1–2 с моделью угловых (скачивание CSV, сборка датасета).
2. `scripts/models/train-goals-markets.py` — две Poisson-регрессии ожидаемых голов хозяев и гостей с хронологическим разбиением train/validation/test. Набор признаков выбирается на validation из четырёх кандидатов (base, +Elo, +затухающие рейтинги, +оба): кандидат должен улучшить суммарную Poisson-девиансу (хозяева + гости) больше чем на мёртвую зону 0.0005; регуляризация подбирается внутри кандидата. Поправка Dixon–Coles (ρ) подбирается grid search'ем (−0.30…0.10, шаг 0.005) по скорректированному правдоподобию на train-предсказаниях и разворачивается только если улучшает validation 1X2 logLoss больше чем на 0.0005. Сравнение с baseline «лиговое среднее голов, разделённое по исторической доле домашних голов». Отчёт: `data/goals_markets_model_validation.json`.
3. `scripts/models/export-goals-runtime.py` — переобучение на полной истории на выбранном на validation наборе признаков и экспорт `data/goals_markets_models.json` (schemaVersion 2): коэффициенты, скейлеры, медианы импутации, свежие признаки команд (включая Elo и затухающие рейтинги), лиговые средние, алиасы лиг; при развёрнутой поправке — `dcRho` на уровне payload.

**Качество (переобучение 3 ноября 2026 г., этап 4: тест с 2024-07-01, 19 272 матча, 24 лиги; train 164 688, validation 17 090).** Выбран набор «base+Elo+затухающие рейтинги» (суммарная validation-девианса 2.2488 против 2.3064 у base; отдельно Elo даёт 2.2540, затухающие рейтинги 2.2706). Развёрнута поправка Dixon–Coles ρ=−0.055: validation 1X2 logLoss 1.00715 → 1.00648 (выигрыш 0.00067, мёртвая зона 0.0005), на тесте 1.01165 → 1.01078. Итоговые метрики с поправкой: 1X2 logLoss 1.0108 против 1.0738 у baseline, Brier 0.6049 против 0.6496. Решения воспроизвелись в точности относительно прогона на 19 лигах (тот же набор признаков и тот же ρ), что говорит об устойчивости выбора к расширению данных. Это исследовательский baseline, а не доказанное преимущество.

**Инференс в браузере (`goals-internal-model.js`).** Для каждого будущего матча модуль тем же способом, что и `internal-model.js`, сопоставляет лигу и команды с обучающими данными, вычисляет λ хозяев и гостей, строит матрицу счёта как произведение независимых распределений Пуассона (0–10 голов); при наличии `dcRho` ячейки 0:0, 0:1, 1:0, 1:1 умножаются на τ-факторы Dixon–Coles, матрица ренормируется, и из неё согласованно выводятся все рынки: П1/Х/П2 — суммы по областям матрицы; двойные шансы — их попарные суммы; общий тотал — хвост суммы голов; индивидуальные тоталы — хвосты Пуассона каждой стороны. Минимальная история команды — 5 матчей.

**Ограничения.** Зависимость голов команд учитывается только поправкой Dixon–Coles на низкие счета (ρ=−0.055 с 3 ноября 2026 г.); остальные ячейки матрицы остаются независимыми. Изотоническая калибровка линий общего тотала оценивалась повторно 3 ноября 2026 г. (этап 4, 24 лиги) и снова не развёрнута: кросс-фит выигрыш внутри validation отрицателен (−0.0071); механизм (`totalsCalibration` в экспорте) готов и включится автоматически при положительном выигрыше в будущих прогонах. Поддерживаются только 24 лиги обучающего набора; неизвестные лиги и команды строки не получают. Elo и затухающие рейтинги вычисляются по семьям стран, поэтому клуб сохраняет их при переходе между дивизизонами; для дебютанта рейтинги атаки/защиты отсутствуют до первого матча и импутируются медианами обучения. Для results-only лиг статистические признаки (удары, угловые и т. п.) всегда импутируются медианами с индикаторами пропуска — вклад в λ дают только результативные признаки (голы, Elo, затухающие рейтинги). Источник RUS (`/new/RUS.csv`) отстаёт от календаря: последний матч в выгрузке на 3 ноября 2026 г. — 2 августа 2026 г., поэтому свежие признаки российских команд устаревают между обновлениями источника. Дания в набор `/new/` не входит (файл недоступен, 404); Скандинавия покрыта только Норвегией и Швецией.

### 7.7. Внутренняя модель фолов, ударов и ударов в створ (с 2 ноября 2026 г.)

**Назначение.** Экспериментальная собственная оценка матчевых тоталов фолов (линии 20.5–28.5), ударов (19.5–27.5) и ударов в створ (7.5–11.5) для предстоящих матчей из `data.json`. Является единственным содержимым страницы `stats-model.html` и не смешивается с API-данными источников.

**Данные.** Тот же поматчевый массив football-data.co.uk и тот же leakage-safe датасет (раздел 7.5): целевые поля HF/AF, HS/AS, HST/AST и скользящие признаки команд. Покрытие этих полей во всех 18 лигах обучающего набора составляет ~99–100% с сезона 2020/21 (в девяти исходных лигах — примерно с 2010/11); более ранние сезоны покрыты частично, строки без целевых полей отфильтровываются флагами доступности.

**Пайплайн (воспроизводимый).**

1. Общие шаги 1–2 с моделью угловых (скачивание CSV, сборка датасета).
2. `scripts/models/train-stats-markets.py` — три независимые счётные регрессии матчевых тоталов с хронологическим разбиением train/validation/test, подбором регуляризации и абляцией судейских признаков только на validation; сравнение с baseline «скользящее среднее лиги» и с NB2-переобучением (GLM statsmodels, дисперсия из остатков обучающей части). Развёртываемое распределение выбирается по среднему logLoss линий на validation с мёртвой зоной 0.0005 в пользу Poisson; изотоническая калибровка линий развёртывается только при честном кросс-фит выигрыше внутри validation. Отчёт: `data/stats_markets_model_validation.json`.
3. `scripts/models/export-stats-runtime.py` — переобучение на полной истории и экспорт `data/stats_markets_models.json` (schemaVersion 2), включая `nbAlpha` и узлы калибраторов, когда они развёрнуты.

**Качество на отложенной выборке (тест с 2024-07-01, ~14,6 тыс. матчей, 18 лиг).** Модель лучше лигового baseline по Poisson-девиансе во всех трёх рынках: фолы 1.185 против 1.278, удары 1.344 против 1.409, удары в створ 1.153 против 1.183. Выбор распределения (2 ноября 2026 г.): фолы переведены на NB2 — средний logLoss линий на validation 0.55624 против 0.55721 у Poisson (на тесте 0.5600, девианса среднего 1.1854 у обоих); удары остаются Poisson — выигрыш NB2 на validation 0.00047 не преодолевает мёртвую зону (и на тесте NB2 хуже по девиансе: 1.3516 против 1.3441); удары в створ остаются Poisson (0.58374 против 0.58406). Изотоническая калибровка не развёрнута: кросс-фит выигрыш внутри validation отрицателен во всех трёх рынках (−0.0055, −0.0098, −0.0043). Это исследовательский baseline, а не доказанное преимущество.

**Инференс в браузере (`stats-internal-model.js`).** Тот же механизм, что и у `internal-model.js`: сопоставление лиги и команд с обучающими данными, линейный предиктор с обучающими скейлерами/медианами, вероятности ТБ/ТМ по распределению рынка (Poisson или NB2 с `nbAlpha`), при необходимости — через калибратор линии. Минимальная история команды — 5 матчей.

**Ограничения.** Поддерживаются только 18 лиг обучающего набора; неизвестные лиги и команды строки не получают. Пуассоновское занижение дисперсии фолов частично снято переводом рынка на NB2 (с 2 ноября 2026 г.).

### 7.8. Мониторинг качества опубликованных прогнозов (с 2 ноября 2026 г.)

**Назначение.** Forward-testing внутренних моделей: фиксация опубликованных вероятностей до начала матчей и их честная оценка после появления результатов. Восстановлено после снятия прежней приостановки (её обоснование относилось к периоду до авторизации источника football-data.co.uk от 2 ноября 2026 г.).

**Сбор.** Workflow `track-internal-predictions.yml` (4 раза в сутки плюс ручной запуск) выполняет `scripts/models/capture-predictions.mjs`: headless-браузер снимает строки всех трёх страниц (`goals-model.html`, `model-v1.html`, `stats-model.html`) на betting-dev и дописывает их в `data/prediction-ledger/YYYY-MM-DD.jsonl` без дубликатов внутри дня. В записи сохраняются сырые тексты ячеек рынков как опубликовано.

**Оценка.** `scripts/models/evaluate-ledger-vs-dataset.mjs` запускается в еженедельном retrain-workflow после обновления датасета: записи дедуплицируются (на матч — последний снимок строго до старта), лига и команды резолвятся через те же runtime-модули и алиасы, что используют страницы, и сопоставляются со строками датасета (дата старта МСК ± 1 день). Считаются logLoss/Brier/средняя вероятность/наблюдаемая частота по каждому рынку и линии, в разрезе лиг; результаты пишутся в `data/prediction-ledger/evaluation-internal.json` и коммитятся вместе с артефактами моделей. Фактические угловые/ЖК/фолы/удары берутся из датасета football-data.co.uk, так как фид `data.json` их не содержит; параллельно остаётся прежний фидовый оценщик `evaluate-predictions.mjs` (только голы, по `actualResult`).

**Ограничения.** Матч попадает в оценку, только если он был опубликован на странице (лига и обе команды в покрытии модели) и сыгран до последнего обновления датасета; оцениваются вероятности с точностью до отображаемых десятых долей процента.

### 7.9. Страница «Экспрессы дня» (с 3 ноября 2026 г.)

**Назначение.** Ежедневный отбор самых проходимых двойников (экспрессов из двух событий) по матчам текущего дня. Является надстройкой над моделью голов (раздел 7.6), а не отдельной моделью: вероятности не пересчитываются, а переиспользуются из `goals-internal-model.js`.

**Отбор (`express-model.js`).** Из `data.json` берутся уникальные будущие матчи дня снимка (календарный день по МСК, совпадающий с `data.date`). Для каждого матча, который модель голов может оценить, извлекаются кандидаты только из «осторожных» рынков: двойные шансы (1X, 12, X2) и тоталы голов (ТБ/ТМ всех экспортированных линий); чистые победы П1/П2 в экспрессы не допускаются. В отбор идут события с вероятностью от 60% (`MIN_LEG_PROBABILITY`). От каждого матча участвует только его сильнейшее событие; публикуется топ-5 пар разных матчей. Для каждого экспресса показываются совместная вероятность (произведение, корреляция между матчами не моделируется) и справедливый коэффициент 1/p — это модельная оценка, а не котировка букмекера. Если подходящих матчей меньше двух, страница честно показывает пустое состояние.

**Value-режим (с 4 ноября 2026 г.).** Workflow «Refresh dev fixture schedule» дополнительно забирает сырые десятичные кэфы Euro365 (`scripts/models/fetch-euro365-odds.py`, секрет `EURO365_API_KEY` в dev-репозитории) в `data/odds.json`: исходы 1X2, двойные шансы и все доступные линии тоталов по каждому событию дня; правила извлечения цен повторяют production-клиент (`scripts/euro365.js`: только кортежи с нулевыми флагами и основной статус линии `s == 0`). Страница сопоставляет кэфы плечам по `eventId` из строк источника Euro365 в `data.json` (`buildEventIndex`); кэфы применяются только при совпадении `odds.date` с датой снимка. Если кэфы есть, включается value-режим: плечо допускается только с EV = p × кэф ≥ 1.00 (`MIN_LEG_EV`), сильнейшим плечом матча считается плечо с максимальным EV (а не с максимальной вероятностью), пары ранжируются по совместному EV, суммарный кэф ограничен сверху (`MAX_COMBINED_ODDS = 4.0`). Кэфы — котировки одного букмекера, а не консенсус рынка; они используются только для отбора и отображения и не смешиваются с вероятностями модели и не участвуют в обучении (раздел 9). Без кэфов страница работает в прежнем режиме максимальной вероятности.

**Ограничения.** Та же зона покрытия, что у модели голов (24 лиги); неизвестные лиги/команды не участвуют. Совместная вероятность предполагает независимость матчей. Рынки статистических моделей (угловые, ЖК, фолы, удары) в отбор не входят. Это исследовательская оценка, а не рекомендация к ставке.

### 7.10. Бэктест модели голов против закрывающих коэффициентов (этап 5, с 3 ноября 2026 г.)

**Назначение.** Проверить, есть ли у модели голов (раздел 7.6) преимущество против закрывающей линии: если бы ставки делались по сигналу модели, был бы результат прибыльным. Скрипт `scripts/models/backtest-closing-odds.py`, отчёт `data/goals_markets_backtest.json` (не коммитить CSV; в репозиторий попадает только JSON-отчёт).

**Методология.** Строго out-of-sample: модель переобучается только на train (≤ 2022-06-30), порог отбора ставок выбирается на validation (2022-07-01…2024-06-30) по максимуму ROI при минимуме 100 ставок, итоговые цифры — только на нетронутом test (≥ 2024-07-01). Коэффициенты берутся из тех же сырых CSV football-data.co.uk: закрывающие Pinnacle (PSCH/PSCD/PSCA, PC>2.5/PC<2.5 — частичное покрытие), Max (MaxC*) и Avg (AvgC* — полное покрытие основных и results-only лиг). Ставка — 1 юнит флэтом; на матч на рынке не более одной ставки (исход с наибольшим edge); edge = p·k − 1; полная сетка порогов edge (0.00/0.02/0.05/0.10) публикуется всегда, а не только выбранная; доверительный интервал ROI — бутстреп по ставкам (2000 повторов, сид 42). Дополнительно модель сравнивается с закрывающим рынком по logLoss на «честных» вероятностях (маржа убрана нормировкой 1/k).

**Результат — отрицательный, и это зафиксировано честно.** Ни одна комбинация рынок × источник коэффициентов × порог не даёт положительного ROI: на test все ROI от −4,5% (тотал 2,5 по MaxC без порога) до −15,3% (1X2 по AvgC с порогом 0,10), и все бутстреп-интервалы целиком ниже нуля. Повышение порога edge систематически ухудшает ROI — то есть чем сильнее модель расходится с рынком, тем чаще неправа именно модель. Сравнение качества вероятностей подтверждает: logLoss модели на test 1,011 против 0,994 у честной закрывающей линии (на validation 1,007 против 0,992) — рынок калиброван лучше модели. **Вывод: закрывающая линия эффективна относительно текущей модели; торгового преимущества у модели нет, и страницы сайта это не обещают.** Отчёт сохраняет полные сетки, чтобы будущие улучшения модели можно было проверить тем же протоколом.

**Ограничения.** Покрытие Pinnacle частичное (особенно в свежих сезонах), поэтому результаты по источникам не вполне сопоставимы между собой. Прошлая неэффективность/эффективность линии могла измениться после обучающего окна. Результат не является рекомендацией к ставкам — наоборот, это измеренное подтверждение, что систематического плюса у модели против закрытия нет.

**Эксперимент с градиентным бустингом (3 ноября 2026 г., отрицательный результат).** Скрипт `scripts/models/experiment-goals-gb.py` проверяет HistGradientBoostingRegressor (loss=poisson) на том же наборе признаков, сплите и мёртвой зоне: сетка из четырёх конфигураций, выбор на validation. Все конфигурации проигрывают линейной Poisson-регрессии (лучшая комбинированная deviance 2,2539 против 2,2488 у baseline; validation 1X2 logLoss 1,0079 против 1,0065). По протоколу мёртвой зоны бустинг отклонён, бэктест против коэффициентов для него не запускался, продакшен-модель не менялась. Вывод: на текущих признаках нелинейности не дают выигрыша — узкое место модели в данных (составы, травмы, xG), а не в алгоритме. Отчёт: `data/goals_markets_gb_experiment.json`.

### 7.11. Еврокубковый этап — Лига чемпионов (с 3 ноября 2026 г.)

**Назначение.** Отдельная модель для матчей ЛЧ: чемпионатные признаки не переносятся напрямую, потому что Elo изолирован по странам, а контекст лиги у еврокубков отсутствует. Решение владельца от 3 ноября 2026 г.: начать с ЛЧ; TheStatsAPI (триал 7 дней, затем возможная месячная подписка) — отложено до возвращения клубных турниров и рассматривается отдельно.

**Данные.** football-data.org API v4 (сборщик `scripts/models/download-fdo-cl.py`, токен только в env `FDO_TOKEN` / GitHub Actions Secrets; сырые JSON не коммитятся, как и CSV). Free-тариф отдаёт ЛЧ за сезоны 2023–2026 (557 завершённых матчей на момент сборки); более старые сезоны недоступны (403). Котировок у источника нет — ROI-бэктест для ЛЧ невозможен, качество оценивается out-of-sample logLoss/Brier против базового среднего ЛЧ.

**Пайплайн.** `scripts/models/build-euro-dataset.py` строит датасет: для каждой команды ЛЧ домашние признаки — состояние на день последнего матча чемпионата строго до даты матча ЛЧ (без утечки), команды стран вне наших 24 лиг получают только euro-признаки с индикаторами пропуска (ничего не выдумывается). Кросс-страновая сравнимость — через отдельный euro Elo (ведётся только по матчам ЛЧ, старт 1500, K=24 с множителем разницы голов, регрессия 25% к среднему между сезонами) и затухающие euro-рейтинги голов (полураспад 75 дней). `scripts/models/train-euro-cl.py` обучает Poisson-регрессию: сплит по сезонам (train 2023+2024, validation 2025, test — завершённые матчи 2026), alpha и развёртывание Dixon–Coles по тем же правилам мёртвой зоны. Отчёт: `data/euro_cl_model_validation.json`.

**Результат валидации.** Модель уверенно лучше базового среднего ЛЧ: validation logLoss 0,932 против 1,024 (Brier 0,552 против 0,617), test logLoss 0,894 против 0,964 (Brier 0,518 против 0,576). Предостережения: выборка тонкая (557 матчей, test ~50 матчей — метрики шумные), Dixon–Coles выбрал ρ=+0,10 (верх границы сетки, отличается от чемпионатного −0,055 — следствие малой выборки). **Публикация (решение владельца от 3 ноября 2026 г.).** Модель опубликована отдельным блоком «Еврокубки»: страница `euro-model.html` (рантайм `euro-internal-model.js`, данные `data/euro_cl_model.json`, экспорт `scripts/models/export-euro-runtime.py` — дообучение на всех 557 матчах с alpha и ρ, выбранными на validation). На странице явно указаны ограничения: тонкая выборка и отсутствие проверки против рынка. Матчи ЛЧ из фида дедуплицируются по каноническим ключам команд евро-модели (один матч из нескольких источников показывается один раз); неизвестные команды и не-ЛЧ турниры (включая «AFC Champions League», «Championship») не оцениваются.

### 7.12. Взвешивание по давности и признак судьи по красным (этап 6, 3 ноября 2026 г.)

**Что сделано.** Общий модуль `scripts/models/recency.py`: экспоненциальные sample weights с полураспадом в днях, нормализованные к среднему 1 (alpha остаётся сопоставимой с невзвешенным обучением); возраст матча отсчитывается от начала validation (в обучении) или от свежайшей даты датасета (в экспорте-рефите). Во всех четырёх train-скриптах полураспад (`None`/`550`/`1100` дней) подбирается на validation совместно с alpha и наборами признаков; взвешивание разворачивается, только если лучший взвешенный вариант бьёт лучший невзвешенный больше чем на мёртвую зону 0,0005 по Poisson deviance. Выбранный полураспад записывается в отчёты (`selected[*].recencyHalfLifeDays`, раздел `recency`/`poissonTuning.recency`) и применяется экспортами при дообучении на полных данных; NB2-рефит получает те же веса через `freq_weights`.

**Признак судьи по красным.** Базовые судейские признаки (`referee_yellows_avg10`, `referee_fouls_avg10`, счётчики) существовали раньше, но абляция на validation их отклоняла. На этом этапе добавлен кандидат `full_plus_referee_red` (полный набор + `referee_red_cards_avg10`).

**Результаты (validation deviance до → после).** Угловые 1,16226 → 1,16113 (развёрнуты half-life 550 и набор `full_plus_referee_red`); карточки 1,12881 → 1,12762 (half-life 1100); фолы 1,13632 → 1,12785 (550); удары 1,29877 → 1,29667 (1100); удары в створ 1,12344 → 1,12008 (550, набор сменился на `without_referee`); голы: взвешивание развёрнуто только для гостей (1100), 1X2 logLoss validation практически не изменился (1,00649), test 1,01078 → 1,01061; ЛЧ: half-life 1100 (хозяева) и 550 (гости), validation logLoss 0,93228 → 0,93208, test 0,89376 → 0,89650 (test-окно ~50 матчей, шумно). Вывод честный: выигрыш мал, но неотрицателен на validation везде, где развёрнут; главный боттleneck по-прежнему данные.

**Тесты.** `tests/test_recency_weights.py` (юнит-тесты весов + синтетический дрейфующий процесс, где взвешенный Poisson точнее на будущем окне).

## 8. Архив результатов без CSV

Скрипт `scripts/models/archive-provider-results.mjs` сохраняет завершённые результаты в JSONL:

- вход: корневой `data.json`;
- каталог: `data/results-ledger/`;
- файл: `YYYY-MM-DD.jsonl`;
- одна запись — одна строка JSON.

### 8.1. Что попадает в архив

Скрипт проверяет поле `actualResult`. Оно должно содержать маркер завершения (например, FT/ФТ/FINISHED) и счёт. Из него извлекаются:

- голы хозяев;
- голы гостей;
- сумма голов;
- фактический исход П1/X/П2;
- угловые, если они присутствуют в распознаваемом формате.

Также сохраняются идентификатор события, источник, команды, лига, время матча, прогнозные поля и исходная строка результата.

### 8.2. Дедупликация

Ключ дедупликации — сочетание `source` и `eventId` в рамках дневного файла. Повторная обработка одного и того же события не должна добавлять вторую запись в этот файл.

### 8.3. Ограничения архива

- Текущий парсер не извлекает фактическое число жёлтых карточек.
- Архивирование зависит от того, передаёт ли входной снимок завершённый результат в поддерживаемом формате.
- Если в снимке нет подходящих завершённых матчей, файл может не появиться или остаться пустым.
- JSONL-архив результатов не является автоматически разрешённым датасетом для обучения: перед использованием нужно проверить права источника и происхождение каждой записи.
- Архивирование прогнозных полей не означает разрешение на их бессрочное хранение, перераспределение или обучение.

Принятые меры: скачивание раз в неделю с паузами и описательным User-Agent; сырые CSV никогда не коммитятся (CI падает при появлении `.csv`); публикуются только производные коэффициенты и агрегированная статистика. При возражении поставщика или выходе проекта за рамки личного исследования решение пересматривается, пайплайн останавливается.

### 9.1. Обязательная процедура для нового источника

Перед использованием источника для обучения или длительного хранения:

1. Зафиксировать точное юридическое лицо поставщика и URL актуальных условий.
2. Проверить разрешение на получение исторических данных и частоту запросов.
3. Проверить право на долгосрочное хранение и создание собственной базы.
4. Проверить прямое разрешение на model training, machine learning, backtesting и evaluation.
5. Проверить права на derived outputs и их публичное отображение.
6. Проверить upstream-поставщиков и ограничения на данные третьих лиц.
7. Уточнить, что происходит с данными и производными результатами после отмены подписки.
8. Обновить `data/source_eligibility.json` с датой и обоснованием.
9. Только после этого добавлять источник в обучающий workflow.

Успешная техническая загрузка данных не означает, что их юридически разрешено использовать для обучения.

## 11. Тестирование

Тесты находятся в `tests/`: `api-consensus.test.cjs`, `internal-model.test.cjs`, `goals-internal-model.test.cjs`, `stats-internal-model.test.cjs`, `euro-internal-model.test.cjs`, `express-model.test.cjs` (Node.js `node:test`) и `test_build_historical_dataset.py`, `test_backtest_closing_odds.py`, `test_euro_cups.py`, `test_euro365_odds.py`, `test_recency_weights.py`, `test_runtime_model_export.py` (Python unittest).

Текущие проверяемые сценарии API-консенсуса:

1. нормализация 1X2 с корректной суммой;
2. отклонение неполной или некорректной тройки 1X2;
3. разделение тоталов по направлению и точной линии;
4. разбор линий угловых;
5. объединение совпадающего матча из двух источников и расчёт двойного шанса;
6. отсутствие выдуманных угловых/карточек при отсутствии входных данных.

Сценарии внутренних моделей (единый набор для трёх рантаймов, плюс специфика рынков):

1. корректность хвоста распределения Пуассона и монотонность вероятностей по линиям;
2. воспроизводимость линейного предиктора со скейлингом и импутацией;
3. сопоставление лиг и команд через алиасы, включая спонсорские названия лиг расширенного набора, кураторские алиасы команд новых лиг, провайдерские названия N1 и results-only лиг (РПЛ-транслитерации, «LA Galaxy»/«LAFC», «Odds BK», «Fortuna Sittard» и т. п.);
4. отказ в сопоставлении названиям-похожестям других дивизионов («Greece. SuperLeague 2», «Liga Portugal 2», «Senegal. Ligue 2», «Turkey. TFF 1. Lig», «Sweden. Superettan», «Brazil. Serie B», «Netherlands. Eerste Divisie», «Norway. Adeccoligaen», «USL Championship»);
5. расчёт вероятностей для полностью сопоставленного матча;
6. запрет выдуманных вероятностей для неизвестной лиги/команды или недостаточной истории;
7. однозначность substring-fallback;
8. эквивалентность нормализации названий экспортёру;
9. хвост NB2 сверен с эталонными значениями scipy, выбор NB2 происходит только по `type: nb2` и расширяет верхние хвосты относительно Пуассона;
10. калибратор линий: линейная интерполяция между узлами, кламп за пределами узлов, применение только к линиям с экспортированными узлами (в модели голов — только к общему тоталу, 1X2 и индивидуальные тоталы не затрагиваются);
11. поправка Dixon–Coles (модель голов): τ-факторы соответствуют определению, отрицательный ρ повышает вероятность ничьей (и наоборот), матрица остаётся нормированной, значения сверены с эталоном scipy, `predict` применяет `dcRho` модели; `buildFeatureContext` передаёт Elo и затухающие рейтинги команд;
12. экспрессы дня (`express-model.test.cjs`): извлечение кандидатов только из двойных шансов и тоталов (без чистых исходов), отсутствие кандидатов для неизвестных команд, фильтрация матчей по дню снимка в часовом поясе МСК (включая границу полуночи), выбор пар строго из разных матчей, порог 60% на плечо, лимит топ-5, пустой результат при недостатке матчей; value-режим — фильтр EV ≥ 1.00, выбор сильнейшего плеча по EV, ранжирование пар по совместному EV, потолок суммарного кэфа, индексация Euro365-событий только по строкам источника Euro365, привязка кэфов к двойным шансам и линиям тоталов, отказ от невалидных цен; прежний режим максимальной вероятности при отсутствии кэфов;
13. загрузчик кэфов Euro365 (`test_euro365_odds.py`): правила цены из кортежа (флаги = 0, статус линии = 0, цена > 1), обнаружение рынков по словарю (включая regex-fallback при перенумерации id), извлечение 1X2/двойных шансов/линий тоталов, отбраковка частичных и неактивных линий, московский календарный день, форматы `event_id`.

Сценарии сборщика датасета (Python):

1. клуб сохраняет скользящую историю при переходе между дивизионами страны;
2. одноимённые клубы разных стран изолированы;
3. лиговые средние и счётчики матчей остаются по-лиговыми;
4. матчи одного дня не попадают в признаки друг друга (нет утечки внутри дня);
5. eligibility новых лиг включён, N1 по-прежнему исключена из статистических моделей;
6. судейские истории остаются по-лиговыми;
7. Elo: новые команды стартуют с 1500, победитель растёт (с множителем разницы голов), матчи одного дня не влияют друг на друга, рейтинг переносится между дивизионами семьи и изолирован между странами;
8. затухающие рейтинги атаки/защиты: недавние матчи весят больше (период полураспада 75 дней), у дебютанта рейтинги отсутствуют, утечки внутри дня нет, перенос между дивизионами семьи работает;
9. results-only адаптер: усечённая схема `/new/{код}.csv` разбирается (сезон из колонки), такие лиги никогда не получают eligibility статистических моделей, Elo/затухающие рейтинги по ним ведутся, смешанные схемы файлов в одном прогоне обрабатываются корректно.

Сценарии бэктеста против закрывающих коэффициентов (`tests/test_backtest_closing_odds.py`, Python unittest):

1. индекс коэффициентов строится по ключу матча из сырых CSV основных и results-only лиг, дробные/пропущенные значения отбрасываются, дубликаты дедуплицируются так же, как в сборщике датасета;
2. вероятности исходов из матрицы счётов нормированы и сверены с эталонными значениями;
3. ставка проходит только при наличии коэффициента и edge не ниже порога (включая нулевой порог: отрицательный edge не берётся), на матч — не более одной ставки (максимум edge), строки без коэффициентов пропускаются, а не импутируются;
4. сводка ROI/проходимости и бутстреп-интервал воспроизводимы при фиксированном сиде;
5. честный logLoss рынка считается после убирания маржи нормировкой 1/k.

Текущий стиль активных таблиц:

- компактные ячейки и небольшой размер шрифта;

## 15. Известные ограничения и технический долг

### 15.1. Точное время в ключе матча

Текущее сопоставление требует одинакового timestamp. Это может снижать количество объединённых источников. Следующий разумный шаг — отдельный модуль сопоставления с допуском по времени, нормализацией названий и строгой проверкой однозначности. Ошибочное объединение двух разных матчей хуже, чем отсутствие консенсуса.

### 15.2. Простое среднее без оценки надёжности

Сейчас источники имеют одинаковый вес. Нет проверенной калибровки и оценки Brier score/log loss по каждому источнику на достаточно большой и независимой выборке. Нельзя назначать веса источникам на основании впечатления или малого количества матчей.

### 15.3. Ограниченное покрытие внутренней модели

Внутренние модели обслуживают только 18 европейских лиг обучающего набора. Матчи остальных лиг (Нидерланды, Бразилия, Америка, вторые дивизионы Португалии/Турции/Греции и др.) прогноза не получают — это осознанное ограничение, а не ошибка отображения. Сопоставление команд зависит от кураторского словаря алиасов; новые команды и переименования требуют пополнения `TEAM_ALIASES`. Сравнение внутренних моделей с прогнозами BSD на общих матчах ещё не автоматизировано — это следующий шаг оценки качества.

### 15.4. Архив результатов пока ограничен

Архиватор сохраняет только распознаваемые завершённые результаты и не извлекает фактические жёлтые карточки. Нужны контроль полноты, аудит ошибок парсинга, сопоставление прогнозов с фактическими событиями и подтверждение прав на использование данных.

### 15.5. Снимок зависит от production

Dev получает текущий `data.json` из production. Изменения формата production-файла могут повлиять на dev. Желательно добавить версионирование схемы и проверку обязательных полей при каждом обновлении.

### 15.6. Отсутствует полноценный backtesting

Наличие архивных результатов, API-консенсуса и валидационного отчёта внутренней модели ещё не означает, что система прошла backtesting в продовых условиях. Для этого необходимы сохранённые прогнозы, корректные фактические результаты, временное разделение выборок, проверка калибровки и анализ по лигам/рынкам/источникам. Валидация внутренней модели выполнена на хронологически отложенной выборке, но это исследовательская оценка, а не ROI-тест.

## 16. Рекомендуемый дальнейший план

Порядок работ, который минимизирует риск ложных выводов:

### Этап A — качество сопоставления событий
- Добавить диагностический отчёт по непарным и объединённым событиям.
- Реализовать безопасное сопоставление при небольшом расхождении времени только для уникальной пары команд.
- Отдельно тестировать одинаковые команды в разных турнирах/датах и неоднозначные пары.
- Не объединять события при конфликте домашней/гостевой стороны.

### Этап B — диагностика консенсуса
- Показывать число уникальных источников для каждого матча и рынка.
- Разделять «одноисточниковый прогноз» и «консенсус».
- Показывать диапазон расхождения источников, медиану и среднее, не подменяя ими друг друга.
- Маркировать подозрительные/неполные тройки вероятностей.
- Не скрывать низкое покрытие за общим количеством записей.

### Этап C — сбор результатов и оценка качества
- Расширить разбор фактических результатов и проверять его на реальных форматах.
- Добавить журнал ошибок и отчёт по полноте архива.
- Сопоставлять сохранённый прогноз с итогом матча без утечки будущей информации.
- Считать Brier score, log loss, calibration/reliability bins и метрики по рынкам.
- Публиковать объём выборки рядом с каждой метрикой.
- Сохранять ежедневные прогнозы внутренней модели угловых/ЖК и оценивать их на фактических данных football-data.co.uk по мере публикации результатов.
- До проверки прав не использовать ограниченные данные для обучения.

### Этап D — внутренние модели
- ✅ Угловые и ЖК: первая воспроизводимая версия запущена (раздел 7.5), хронологическая валидация и отчёт приложены.
- Следующие шаги: NB2/калибровка по линиям на живых данных, сравнение с BSD на общих матчах, расширение лиг при достаточном покрытии.
- Исходы 1X2: отдельная модель на разрешённых данных (openfootball, ClubElo, international_results) — кандидат на следующую итерацию; сравнивать с простым baseline и API-консенсусом.
- Вводить модель в интерфейс только после воспроизводимой оценки и достаточного покрытия.

### Этап E — надёжность эксплуатации
- Версионировать схему `data.json`.
- Добавить мониторинг устаревшего снимка и ошибок загрузки.
- Проверять, что Pages опубликован после успешной валидации.
- Сохранять краткий changelog и дату последнего успешного расчёта.

## 17. Термины

- **API-консенсус** — простое агрегирование прогнозных вероятностей нескольких API-источников.
- **Источник** — поставщик исходных данных или прогнозов, например BSD.
- **Исходная запись** — одна строка прогноза в `data.json`.
- **Уникальный источник** — distinct provider name после группировки матча.
- **Линия** — порог тотала, например 2.5 гола или 9.5 угловых.
- **Двойной шанс** — объединение двух исходов 1X2.
- **DNB** — ставка без учёта ничьей; вероятность нормируется на две неничейные стороны.
- **JSONL** — текстовый файл, где каждая строка является самостоятельным JSON-объектом.
- **Backtesting** — ретроспективная оценка прогнозов на фактических результатах.
- **Калибровка** — соответствие прогнозируемых вероятностей фактической частоте наступления событий.
- **Внутренняя модель** — воспроизводимый обученный компонент с документированным источником, тестами и отчётом оценки (сейчас: Poisson-регрессия угловых и ЖК).
- **Production** — основное приложение; **dev** — отдельная экспериментальная среда.

## 18. Ключевые правила, которые нельзя нарушать

1. Не вносить изменения в production без отдельного разрешения.
2. Не коммитить CSV в репозиторий; не включать старые отключённые модели (`goals-model.js`, `model-v1.js`, goals-артефакты).
3. Не подключать Api-Football.
4. Не выдумывать вероятности отсутствующих рынков.
5. Не выдавать один источник за консенсус.
6. Жёлтые карточки показывать только через проверенную внутреннюю модель или реальные входные вероятности.
7. Не возвращать красные карточки и точный счёт в прогнозный интерфейс.
8. Не показывать форы в активных таблицах без отдельного решения.
9. Не использовать данные для обучения вне зафиксированных в `data/source_eligibility.json` решений; изменение прав — только с датой и обоснованием.
10. Не называть API-консенсус внутренней обученной моделью.
11. Не считать визуальную подсветку вероятности выше 65% рекомендацией к ставке.
12. При каждом изменении расчёта добавлять тесты и проверять опубликованный результат.
13. Внутреннюю модель показывать только отдельным помеченным блоком и только для матчей, сопоставленных с обучающими данными.
